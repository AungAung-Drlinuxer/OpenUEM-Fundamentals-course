# Module 08 — လေ့ကျင့်ခန်းများ

ဤ လေ့ကျင့်ခန်း ခြောက်ခုသည် `lab.py` ရှိ fixture များကို အသုံးပြုသည်။ လေ့ကျင့်ခန်း တစ်ခုစီတွင် function တစ်ခု ရေးပြီး `assert` ဖြင့် ရလဒ်ကို စစ်ဆေးရသည်။ Run ရန် —

```bash
python3 modules/08_patch_automation/lab.py
```

## Exercise 1 — Pending update စာရင်း ခွဲခြမ်းစိတ်ဖြာခြင်း

`PENDING_UPDATES` fixture တွင် endpoint တစ်ခုစီအတွက် severity အလိုက် pending update အရေအတွက် ပါဝင်သည်။

လုပ်ဆောင်ရန် —

1. Endpoint တစ်ခုစီ၏ စုစုပေါင်း pending update အရေအတွက် တွက်ပါ။
2. Severity တစ်ခုစီ၏ fleet စုစုပေါင်း (critical၊ important၊ moderate၊ low) တွက်ပါ။
3. Endpoint စာရင်းကို အမည်အလိုက် စီပြီး စုစုပေါင်းနှင့်အတူ ပြပါ။
4. Critical အရေအတွက် အများဆုံး endpoint နှစ်ခုကို ဦးစားပေး စာရင်းအဖြစ် ရွေးပါ။

စစ်ဆေးရန် — fleet စုစုပေါင်းသည် 31 ဖြစ်ရမည်။ Critical စုစုပေါင်းသည် 8 ဖြစ်ရမည်။ အနည်းဆုံး pending ရှိသော endpoint သည် `MB-CEO-01` ဖြစ်ရမည်။

## Exercise 2 — Maintenance window ရရှိနိုင်မှု တွက်ချက်ခြင်း

`MAINTENANCE_WINDOWS` တွင် window များကို UTC ဖြင့် သတ်မှတ်ထားသည်။ အချို့ window များသည် သန်းခေါင်ကျော်သည်အထိ ဆက်သည်။ `ENDPOINT_OFFSETS` တွင် endpoint တစ်ခုစီ၏ UTC offset ပါဝင်သည်။ `REFERENCE_NOW` သည် ပုံသေ အခိုက်အတန့် ဖြစ်သည်။

လုပ်ဆောင်ရန် —

1. Endpoint တစ်ခုစီ၏ local time ကို offset ဖြင့် တွက်ပါ။
2. Window အတွင်း ရှိမရှိ ဆုံးဖြတ်သည့် function တစ်ခု ရေးပါ။ သန်းခေါင်ကျော် window ကို မှန်ကန်စွာ ကိုင်တွယ်ရမည်။
3. Window စတင်ချိန်ကို အတွင်းဟု သတ်မှတ်ပြီး ပြီးဆုံးချိန်ကို အပြင်ဟု သတ်မှတ်ပါ။
4. Endpoint တစ်ခုစီအတွက် ရရှိနိုင်သော window အမည်များကို စီပြီး ပြပါ။

စစ်ဆေးရန် — `MB-CEO-01` သည် `windows-ring-1` ကို ရရှိရမည်။ `SRV-DB-01` သည် သန်းခေါင်ကျော် window ဖြစ်သော `linux-ring-1` ကို ရရှိရမည်။ `WS-ACC-01` တွင် ရရှိနိုင်သော window မရှိရ။

## Exercise 3 — Criticality အလိုက် patch wave စီစဉ်ခြင်း

`UPDATE_BACKLOG` တွင် patch တစ်ခုစီ၏ severity နှင့် reboot လိုအပ်မှု ပါဝင်သည်။ Wave စည်းမျဉ်းမှာ critical → wave 1၊ important → wave 2၊ moderate နှင့် low → wave 3 ဖြစ်သည်။

လုပ်ဆောင်ရန် —

1. Patch တစ်ခုစီအတွက် wave သတ်မှတ်ပါ။
2. Window ကြာချိန်ကို တွက်ပါ — အခြေခံ မိနစ် 30၊ reboot လိုအပ်ပါက မိနစ် 60 ထပ်တိုးပါ။
3. Wave တစ်ခုအတွင်း reboot လိုအပ်သော patch ကို အရင်ထားပါ။ ထို့နောက် severity၊ ထို့နောက် အမည်အလိုက် စီပါ။
4. Wave တစ်ခုစီ၏ အဖွဲ့ဝင် အရေအတွက်နှင့် လိုအပ်သော window ကြာချိန် အများဆုံးကို ပြပါ။

စစ်ဆေးရန် — wave 1 တွင် patch နှစ်ခု ရှိရမည်။ wave 3 တွင် patch လေးခု ရှိရမည်။ wave 1 ၏ window သည် မိနစ် 90 ဖြစ်ရမည်။

## Exercise 4 — Validation matrix အကဲဖြတ်ခြင်း

`POST_DEPLOY_OBSERVATIONS` တွင် deployment ပြီးနောက် တိုင်းတာရရှိသော အချက်များ ပါဝင်သည်။ `VALIDATION_RULES` တွင် စစ်ဆေးချက် ငါးခု ပါဝင်သည်။

လုပ်ဆောင်ရန် —

1. Endpoint တစ်ခုစီကို စစ်ဆေးချက် ငါးခုဖြင့် အကဲဖြတ်ပါ။
2. ကျရှုံးသော စစ်ဆေးချက် အမည်များကို စီပြီး သိမ်းပါ။
3. စစ်ဆေးချက် အားလုံး၏ စုစုပေါင်း အောင်မြင်မှု အရေအတွက် တွက်ပါ။
4. `service_healthy` ကျရှုံးသော endpoint ကို rollback လိုအပ်သည်ဟု သတ်မှတ်ပါ။

စစ်ဆေးရန် — စုစုပေါင်း စစ်ဆေးချက်သည် 15 ဖြစ်ရမည်။ အောင်မြင်မှုသည် 11 ဖြစ်ရမည်။ Rollback လိုအပ်သော endpoint သည် `SRV-APP-01` တစ်ခုတည်း ဖြစ်ရမည်။

## Exercise 5 — Compliance ရာခိုင်နှုန်း တွက်ချက်ခြင်း

`COMPLIANCE_ROWS` တွင် endpoint တစ်ခုစီအတွက် လိုအပ်သော patch အရေအတွက်၊ တပ်ဆင်ပြီး အရေအတွက်နှင့် ကျန်ရှိ critical အရေအတွက် ပါဝင်သည်။ Compliance သတ်မှတ်ချက်မှာ patch rate 95 ရာခိုင်နှုန်း အထက်နှင့် critical pending သုည ဖြစ်သည်။

လုပ်ဆောင်ရန် —

1. Endpoint တစ်ခုစီ၏ patch rate ကို ဆယ်ပုံတစ်ပုံ တိကျမှုဖြင့် တွက်ပါ။
2. Compliance သတ်မှတ်ချက် ပြည့်မပြည့် ဆုံးဖြတ်ပါ။
3. Fleet patch rate ကို တပ်ဆင်ပြီး စုစုပေါင်းနှင့် လိုအပ်သော စုစုပေါင်း အချိုးဖြင့် တွက်ပါ။
4. Endpoint compliance ရာခိုင်နှုန်းနှင့် သတ်မှတ်ချက် မပြည့်သော endpoint စာရင်းကို ထုတ်ပါ။

စစ်ဆေးရန် — fleet patch rate သည် 94.4 ရာခိုင်နှုန်း ဖြစ်ရမည်။ Endpoint compliance သည် 60.0 ရာခိုင်နှုန်း ဖြစ်ရမည်။ Exception စာရင်းတွင် endpoint နှစ်ခု ပါရမည်။

## Exercise 6 — Automation trigger ရွေးချယ်ခြင်း

`AUTOMATION_JOBS` တွင် လုပ်ငန်းတစ်ခုစီ၏ အတိုင်းအတာ (fleet သို့မဟုတ် single)၊ ထပ်ခါတလဲလဲ ဖြစ်မှု (continuous သို့မဟုတ် one-off) နှင့် desired state လိုအပ်မှု ပါဝင်သည်။

လုပ်ဆောင်ရန် —

1. Endpoint တစ်ခုတည်းအတွက် တစ်ကြိမ်တည်း လုပ်ဆောင်ရမည့် အလုပ်ကို deployment ဟု သတ်မှတ်ပါ။
2. ကျန်အလုပ်များထဲမှ desired state လိုအပ်ပါက profile ဟု သတ်မှတ်ပါ။
3. ကျန်အလုပ်များကို report ဟု သတ်မှတ်ပါ။
4. Trigger တစ်ခုစီအောက်ရှိ အလုပ်အမည်များကို စီပြီး ပြပါ။ ထို့အပြင် profile စစ်ဆေးမှုနှင့် report ပို့မှု တစ်ရက်လျှင် အကြိမ်ရေ တွက်ပါ။

စစ်ဆေးရန် — trigger သုံးမျိုးလုံးတွင် အလုပ် နှစ်ခုစီ ရှိရမည်။ Profile စစ်ဆေးမှုသည် တစ်ရက်လျှင် 48 ကြိမ်၊ report သည် 24 ကြိမ် ဖြစ်ရမည်။
