# Module 03 — လေ့ကျင့်ခန်းများ

ဤ လေ့ကျင့်ခန်း ၆ ခုသည် `lab.py` ထဲက fixture များကို အသုံးပြုသည်။ လေ့ကျင့်ခန်း
တစ်ခုချင်းကို မိမိကိုယ်တိုင် ရေးပြီးမှ `solution.md` နှင့် နှိုင်းယှဉ်သင့်သည်။
Output များသည် deterministic ဖြစ်ရမည် — set သို့မဟုတ် dict ကိုပြမီ sort
လုပ်ရသည်။

## Exercise 1 — Package မှ Component Role သို့ ပုံဖော်ခြင်း

`PACKAGE_ROLES` fixture တွင် package အမည်များနှင့် ၎င်းတို့၏ တာဝန်၊ inbound
port များ ပါဝင်သည်။ `REQUESTED_PACKAGES` စာရင်းထဲတွင် OpenUEM package မဟုတ်သော
အမည် တစ်ခု ရောနေသည်။

လုပ်ရန် —

1. Package အမည်ကို အက္ခရာစဉ်အလိုက် စီပြီး တာဝန် နှင့် port ကို ဇယားပုံစံ
   ဖြင့် ပြပါ။ Port မရှိသော component အတွက် `-` ကို ပြပါ။
2. Fixture တွင် မပါသော အမည်ကို `UNKNOWN PACKAGE` ဟု မှတ်ပြီး သီးခြား ရေတွက်ပါ။
3. Mapping လုပ်နိုင်သည့် package အရေအတွက် နှင့် မလုပ်နိုင်သည့် အရေအတွက်ကို
   ပြပါ။
4. Inbound port အားလုံးကို စီပြီး ပြပါ။

လက်ခံနိုင်သည့် အခြေအနေ — `openuem-console` သည် port နှစ်ခု (1323 နှင့် 1324)
ရှိရမည်။ Inbound port စာရင်းတွင် 4433 နှင့် 8000 ပါရမည်။ Worker များအတွက်
port မရှိကြောင်း အတည်ပြုရမည်။

## Exercise 2 — Service စတင်သည့် အစီအစဉ် စစ်ဆေးခြင်း

`DOCUMENTED_ORDER` သည် official documentation ၏ အစီအစဉ် ဖြစ်သည်။
`DEPENDENCIES` သည် "မည်သည့် service က မည်သည့် service မတိုင်မီ စတင်ရမည်"
ဆိုသည့် အတွဲများ ဖြစ်သည်။

လုပ်ရန် —

1. အစီအစဉ် တစ်ခုကို လက်ခံပြီး အတွဲတစ်ခုချင်းစီအတွက် ချိုးဖောက်မှု ရှိမရှိ
   စစ်သည့် function တစ်ခု ရေးပါ။
2. `DOCUMENTED_ORDER` အတွက် ချိုးဖောက်မှု သုည ဖြစ်ကြောင်း အတည်ပြုပါ။
3. `PROPOSED_ORDER` (console ကို ရှေ့ဆုံးတွင် ထားသည့် အစီအစဉ်) အတွက်
   ချိုးဖောက်မှုများကို စီပြီး ပြပါ။ ချိုးဖောက်မှု တစ်ခုချင်းကို
   `<service> starts before <service>` ပုံစံဖြင့် ရေးပါ။
4. Documentation အစီအစဉ်သည် dependency အတွဲများထဲက service အားလုံးကို
   လွှမ်းခြုံမှု ရှိကြောင်း စစ်ပါ။

လက်ခံနိုင်သည့် အခြေအနေ — ချိုးဖောက်မှု နှစ်ခု တိတိကျကျ ထွက်ရမည်။
`openuem-console` သည် `openuem-server-updater` နှင့် `openuem-ocsp-responder`
တို့၏ ရှေ့တွင် စတင်နေမှုကို ဖော်ပြရမည်။

## Exercise 3 — `openuem.ini` ကို Section အလိုက် ခွဲခြမ်းခြင်း

`INI_FIXTURE` တွင် section မတိုင်မီ key များ၊ `[Console]` နှင့် `[JWT]` ပါဝင်သည်။
`REQUIRED_INI` သည် မရှိမဖြစ် လိုအပ်သည့် entry များ ဖြစ်သည်။

လုပ်ရန် —

1. `#` နှင့် `;` comment များကို ကျော်ပြီး `[section]` နှင့် `key = value` ကို
   ဖတ်သည့် parser ကို ရေးပါ။ Section မတိုင်မီ key များကို `(global)` အောက်တွင်
   ထည့်ပါ။
2. `port`၊ `authport` နှင့် `reverseproxyauthport` ကို integer အဖြစ် ပြောင်းပါ။
3. Console ၏ hostname၊ port၊ authport၊ domain နှင့် reverse proxy အတွဲကို
   ပြပါ။
4. `[JWT] Key` ၏ အရှည်ကို ပြပါ။
5. `REQUIRED_INI` ထဲက မည်သည့် entry မရှိသည်ကို စာရင်းပြပါ။ ထို့နောက်
   `authport` နှင့် `JWT Key` ကို ဖျက်ထားသော မိတ္တူတစ်ခု ဖန်တီးပြီး
   ထို မိတ္တူအတွက် လိုအပ်ချက် နှစ်ခု ပျောက်နေကြောင်း ပြပါ။

လက်ခံနိုင်သည့် အခြေအနေ — section သုံးခု (`(global)`၊ `Console`၊ `JWT`) ရရမည်။
`port` နှင့် `authport` သည် integer ဖြစ်ရမည်။ Broken မိတ္တူတွင်
`Console.authport` နှင့် `JWT.Key` ပျောက်နေရမည်။

## Exercise 4 — `--years-valid` မှ သက်တမ်းကုန်ဆုံးရက် တွက်ချက်ခြင်း

`YEARS_VALID_CASES` တွင် ထုတ်ပေးသည့် ရက် နှင့် သက်တမ်း (နှစ်) အတွဲများ ရှိသည်။

လုပ်ရန် —

1. ရက် တစ်ခုအပေါ် နှစ် ပေါင်းသည့် helper ကို ရေးပါ။ ဖေဖော်ဝါရီ 29 ရက်နေ့
   အတွက် နောက်နှစ်တွင် ထို ရက် မရှိသောကြောင့် 28 ရက်သို့ ချိန်ညှိရသည်။
2. သက်တမ်း ၁ နှစ် အောက် ဖြစ်သော အခြေအနေကို ငြင်းပယ်ပါ။
3. ထုတ်ပေးရက်၊ သက်တမ်း၊ သက်တမ်းကုန်ဆုံးရက် နှင့် ရက် အရေအတွက်ကို
   တစ်ကြောင်းစီ ပြပါ။ Leap day ချိန်ညှိမှု ဖြစ်ခဲ့ပါက `leap_day_clamped=yes`
   ကို ထည့်ပါ။
4. သက်တမ်း ပိုရှည်သည့် certificate သည် ပိုနောက်ကျမှ ကုန်ဆုံးကြောင်း စစ်ပါ။

လက်ခံနိုင်သည့် အခြေအနေ — 2026-03-15 မှ ၂ နှစ်သည် 2028-03-15 ဖြစ်ပြီး ရက်
ပေါင်း 731 ရှိရမည်။ 2024-02-29 မှ ၁ နှစ်သည် 2025-02-28 ဖြစ်ရမည်။

## Exercise 5 — Console/Auth/NATS/OCSP Port ထပ်နေမှု ရှာခြင်း

`PORT_PLAN` သည် server ၏ တရားဝင် inbound port စီမံချက် ဖြစ်သည်။
`EXTRA_LISTENERS` တွင် ထပ်နေနိုင်သည့် အရာနှစ်ခု ထည့်ထားသည်။

လုပ်ရန် —

1. `(port, protocol)` အတွဲကို key အဖြစ် ထား၍ listener များကို အုပ်စုဖွဲ့ပါ။
2. အုပ်စုတစ်ခုတွင် ပိုင်ရှင် နှစ်ဦး အထက် ရှိပါက ထပ်နေမှု အဖြစ် သတ်မှတ်ပါ။
3. ထပ်နေမှုများကို port အလိုက် စီပြီး ပိုင်ရှင်များကို အက္ခရာစဉ်ဖြင့် ပြပါ။
4. Port နံပါတ် တူညီသော်လည်း protocol မတူသည့် အတွဲကို ထပ်နေမှု မဟုတ်ကြောင်း
   သီးခြား ပြပါ။
5. 1024 အောက် port များကို စာရင်းပြပါ။

လက်ခံနိုင်သည့် အခြေအနေ — ထပ်နေမှု တစ်ခုသာ ရှိရမည် (1323/tcp)။ 4433/udp သည်
ထပ်နေမှု မဟုတ်ကြောင်း အတည်ပြုရမည်။ Privileged port စာရင်းတွင် 443 ပါရမည်။

## Exercise 6 — Port စီမံချက်မှ Firewall စည်းမျဉ်း ထုတ်ခြင်း

`PORT_PLAN` ကို အသုံးပြု၍ `ufw` စည်းမျဉ်း စာရင်း ထုတ်ရမည်။

လုပ်ရန် —

1. Port အလိုက် စီထားသော စည်းမျဉ်း စာရင်း ဖန်တီးပါ။ ပုံစံမှာ
   `ufw allow <port>/<proto> comment '<component> <role>'` ဖြစ်သည်။
2. စာရင်း၏ ရှေ့တွင် `ufw default deny incoming` ကို ပြပါ။
3. စည်းမျဉ်း အရေအတွက်၊ အနိမ့်ဆုံး port နှင့် အမြင့်ဆုံး port ကို ပြပါ။
4. ထို စာရင်းကို ဒုတိယ အကြိမ် ထုတ်ပါ။ နှစ်ကြိမ် ရလဒ် ထပ်တူ ဖြစ်ရမည်။

လက်ခံနိုင်သည့် အခြေအနေ — စည်းမျဉ်း ၅ ခု ထွက်ရမည်။ Port ငါးခုလုံး တစ်ကြိမ်
စီသာ ပါရမည်။ အနိမ့်ဆုံး 443၊ အမြင့်ဆုံး 8000 ဖြစ်ရမည်။
